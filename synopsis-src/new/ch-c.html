7. System Architecture and UML Design

7.1 Architecture Overview

The system follows a three-tier, layered architecture (Figure 7.1). The presentation tier is a Next.js (React + TypeScript) web application communicating with the back end only through a versioned REST API. The application tier is a FastAPI (Python) service in layers — API routers receive requests, a service layer executes business logic, and a repository layer alone talks to the database through SQLAlchemy. Within it, the deterministic detection engine performs the complete analysis with no external dependency. The data tier is PostgreSQL plus document storage (local disk in development, managed object storage in production). External services (email, CAPTCHA, error monitoring, and optional user-configured AI providers) sit only at the edges.

7.2 Module Description

The back end is organised into modules with single responsibilities: Authentication (registration, email verification, login/logout, refresh-token rotation with reuse detection, password reset/change, account deletion); SRS input and documents (pasted-text analyser; PDF/DOCX/TXT upload with validation, extraction and storage); Segmentation; Detection engine (eleven detectors, deduplication, scoring, health dimensions); Report, history and dashboard; Credential vault and enhancement (encrypted credential storage/testing; optional overview and rewrites with disclosure); and Settings and privacy (profile, data export, history purge, retention, account deletion).

7.3 Analysis Pipeline

  1. The user submits SRS text or an uploaded document; documents are validated and their text extracted.
  2. The text is normalised and segmented deterministically into individual requirements.
  3. All eleven detectors examine every requirement, producing findings (phrase, offsets, severity, reason, recommendation).
  4. Findings are deduplicated: exact duplicates collapse; identical spans from two detectors keep the higher severity.
  5. Scores are computed per requirement (100 minus fixed deductions); the analysis score is their mean, with band and health dimensions derived from the same deductions.
  6. Results are stored in PostgreSQL under the user’s ownership and the report is rendered, with optional enhancement where configured.

8. Database Design

8.1 Design Principles

  • PostgreSQL 16; schema as SQLAlchemy models, created and evolved only via Alembic migrations.
  • Every table has an application-generated UUID primary key, identical on local and managed PostgreSQL.
  • Every user-owned table carries owner_id referencing users(id) with ON DELETE CASCADE; ownership is enforced in SQL and again in the API layer.
  • Status columns are short text fields guarded by CHECK constraints (not database enums), keeping migrations simple; scores are constrained to 0–100.
  • Timestamps are UTC; deletion is real deletion; indexes follow real query paths (owner + time, owner + score, analysis + category).

8.3 Normalisation, Integrity and Protection

The schema is in third normal form: user facts live once in users; requirements belong to one analysis; issues to one requirement. Two documented exceptions serve read performance (denormalised counters; JSONB summaries), both written in the same transaction as the findings they summarise.

Integrity is protected at three levels: database constraints reject invalid rows; repositories always filter by owner, so cross-user access returns “not found”; and transactions commit or roll back as a unit. Passwords, tokens and provider keys are stored only as hashes or ciphertext, so a database leak exposes no usable secret. Deleting an analysis cascades to its requirements, issues and orphaned file; deleting the account removes everything.
