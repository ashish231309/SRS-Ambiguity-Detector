4. Literature and Background Study

4.1 The SRS and Its Quality Characteristics

IEEE Std 830-1998, IEEE Recommended Practice for Software Requirements Specifications, states that a good SRS should be correct, unambiguous, complete, consistent, verifiable, modifiable and traceable [1]; an SRS is unambiguous if every requirement in it has only one interpretation. Its successor, ISO/IEC/IEEE 29148:2018, likewise requires each requirement to be singular, unambiguous, complete and verifiable [2]. Wiegers and Beatty, and Sommerville, likewise stress that every reader must arrive at the same understanding of a requirement [7][8]. This project takes that classical quality characteristic and turns it into an automatic check.

4.2 Nature of Ambiguity in Requirements

Berry and Kamsties, in their widely cited study, distinguish several forms of ambiguity in requirements [3]: lexical (a word with more than one meaning), syntactic (more than one parse, as with careless “and/or”), semantic and scope (unclear quantities, “several users”, “all reports”), and referential (pronouns such as “it” with no clear antecedent). Practical writing adds weaknesses with the same effect: subjective words (“fast”, “user-friendly”), optional wording (“may”, “if possible”), absolutes (“always”, “never”), passive constructions hiding the responsible actor (“shall be approved”), and claims with no measurable criterion, which nobody can verify against the finished system. The eleven detectors of the proposed system were selected to cover these practical categories.

4.3 Requirements Smells and Automated Quality Checks

Detecting weak requirement language automatically is established in the literature as requirements smells: Femmer and co-authors define a smell as an indicator of a quality violation detectable by lightweight static analysis, and show such patterns can be found automatically [4]. Earlier, the QuARS tool applied natural-language processing to evaluate ambiguity and completeness of requirements [5], and NASA’s ARM tool measured requirement-quality indicators in large specifications [6]. These works establish two facts on which this project builds: much requirement weakness is pattern-based and machine-detectable, and automatic findings must remain explainable review aids.

4.4 Other Existing Approaches

  • Manual peer review and checklists: effective in expert hands, but slow and inconsistent over long documents.
  • Enterprise requirements suites (e.g., IBM DOORS, Jama Connect): powerful but costly, enterprise-oriented tools unavailable to students and small teams.
  • Generic writing assistants: improve prose style but know nothing of measurability, responsible actors or requirement completeness.
  • General-purpose chatbot services: comments vary from run to run, no stable score or stored history is produced, and confidential SRS text must be pasted into a third-party service.

4.5 Gap Identified

The study shows a clear gap: no lightweight, freely usable web tool combines checks against a defined set of ambiguity categories, phrase-level explanation with reason and remedy, a transparent and reproducible quality score, the document formats actually used (PDF, DOCX, TXT), a private history of analyses, and deterministic results that do not change between runs. The proposed system fills exactly this gap, keeping an optional, user-controlled enhancement for generative suggestions in addition to the deterministic findings.

5. Existing and Proposed System

5.1 Existing System

In current practice for most students and small teams, an SRS is written in a word processor and reviewed manually: one or two reviewers read the document and mark doubtful sentences, with no fixed checklist of ambiguity patterns, no measurement of overall quality, and no record of improvement between drafts. Tool support, where it exists, is either a generic grammar checker that does not understand requirements, or an enterprise suite whose cost and administration put it out of reach.

5.2 Proposed System

The proposed system, SRS Ambiguity Detector, is a full-stack web application that performs this first-level review automatically and consistently. A registered user pastes SRS text or uploads a PDF, DOCX or TXT document. The input is normalised and segmented deterministically into individual requirements. Eleven rule-based detectors examine every requirement and record findings with the matched phrase, character offsets, severity, reason and recommendation; duplicates are removed by fixed rules. Each requirement starts at 100 points and loses fixed points per issue (Low 5, Medium 10, High 15, Critical 20); the analysis score is the mean of requirement scores, presented with an ambiguity band and four health dimensions — measurability, specificity, clarity and completeness. The report is saved to PostgreSQL, appears in the user’s history and dashboard, and can be reopened at any time. If the user has stored provider credentials, an optional enhancement may add an overview and rewrite suggestions, clearly disclosed; the deterministic findings remain authoritative in all cases.

5.4 Advantages of the Proposed System

  • Review time drops from hours of reading to a few seconds of automatic analysis.
  • Findings are explainable: the exact phrase, why it was flagged, and how to improve it.
  • The transparent score (no hidden weighting) makes draft-by-draft improvement measurable.
  • Deterministic behaviour makes results trustworthy and comparable, with document upload, history and dashboard making it a continuing work tool.

6. Feasibility Study and Requirement Analysis

6.1 Technical Feasibility

The system uses mature, open-source technologies: Next.js with React and TypeScript for the front end; Python with FastAPI, Pydantic and SQLAlchemy for the back end; PostgreSQL as the database; and Alembic for migrations. The detection engine needs no specialised hardware or paid library — it is deterministic text processing on an ordinary server — and document extraction uses established open-source parsers for PDF and DOCX. All components were installed, executed and tested on a normal development computer, and the production topology uses standard managed services. The project is technically feasible, and has in fact been implemented and verified (Chapters 9 and 10).

6.2 Economic Feasibility

Cost ItemEstimate

Development and initial operating cost is negligible against hours of manual review saved on every SRS, so the project is economically feasible.

6.3 Operational Feasibility

The system runs in an ordinary web browser with no user installation. Its workflow (register, verify, log in, analyse, read the report) needs no training, and report language is deliberately plain. Administrator operation consists of standard, documented tasks: deploying updates, applying migrations and reviewing error reports. The system is operationally feasible for its intended users.

6.5 Legal and Ethical Feasibility

The system processes only documents that users themselves upload, and gives users export and permanent-deletion facilities, supporting responsible data handling in line with the principles of India’s Digital Personal Data Protection Act, 2023. Provider credentials are stored only in encrypted form. All components are open source, used under their licences, and findings are honestly presented as heuristic indicators rather than guarantees. The project is legally and ethically feasible.
