9.2 Detection Engine Implementation

The engine is a registry of eleven independent detector functions. Each receives one requirement and returns findings (category, severity, phrase, offsets, reason, recommendation); new categories register as one more function.

DetectorWhat It DetectsExample (flagged phrase in bold)
vague-quantifierQuantity words: “some”, “many”, “few”, “several”“The system shall support several users.”
subjective-termSubjective words: “fast”, “quickly”, “user-friendly”“The system shall respond quickly.”
missing-measurable-criteriaQuality claims with no measurable criterion“The system shall load reports efficiently.”
pronoun-referencePronouns whose referent may be unclear“When the service receives a request, it validates it.”
optional-language“may”, “might”, “could”, “if possible”, “as needed”“The system may send an alert if possible.”
ambiguous-operator“and/or”, “etc.”, ambiguous “or”“The user can export PDF and/or CSV reports.”
undefined-terminologyCapitalised/domain terms without definition“The system shall notify Premium Users.”
absolute-languageAbsolutes: “always”, “never”, “all”, “every”, “instant”“The system shall always be available.”
passive-actorPassive constructions, unclear actor“The report shall be approved before release.”
missing-constraintBehaviour lacking constraints (limits, timing)“The system shall store audit logs.”
incomplete-requirementFragments, placeholders (“TBD”), dangling modals“The system shall TBD.”

Findings are deduplicated deterministically (exact duplicates collapse; identical spans keep the higher severity). Scoring is transparent:

Requirement score = max (0, 100 − Σ severity deductions), where Low = 5, Medium = 10, High = 15, Critical = 20.  Analysis score = mean of requirement scores. Bands: 80–100 Low, 60–79 Moderate, 40–59 High, 0–39 Very high ambiguity. The same deductions feed four health dimensions — Measurability (subjective terms, missing criteria), Specificity (vague quantifiers, undefined terms, absolutes), Clarity (pronouns, operators, optionals, passives), Completeness (missing constraints, incomplete requirements).

9.3 Back-End and Front-End Implementation

The back end exposes a versioned REST API under /api/v1 (authentication, analysis, documents, dashboard, provider credentials, settings/privacy, health). Routers validate via Pydantic schemas, services run business logic in transactions, repositories hold all database access. Uploads pass validation (type, magic bytes, 10 MB streamed cap, extraction budget) before entering the same pipeline; downloads use signed links expiring in 15 minutes. The front end has server-rendered public pages and signed-in pages (analyser, reports, history, dashboard, settings), a typed API client, cookie-based authentication (never browser storage) and a responsive layout. The production build compiles all 19 routes with type checking.

9.5 Deployment

In production: front end on a managed web host (Vercel), back end on a Python service host, with managed PostgreSQL and object storage. Steps: (1) create database and storage bucket; (2) configure environment variables (never commit secrets); (3) apply migrations with alembic upgrade head; (4) start the back end behind HTTPS; (5) deploy the front end; (6) verify the main flows live.

9.6 Maintenance

  • Corrective: error monitoring (secrets scrubbed) reports faults; layered structure allows safe fixing.
  • Adaptive: pinned dependencies, audited periodically; database changes only via migrations.
  • Perfective/Preventive: detector rules refined from observed false positives; provider backups and full test-suite runs before any release.

10. Security, Privacy, Testing and Quality Assurance

10.1 Security Measures and Threat Mitigation

  • Passwords are stored only as Argon2id hashes; the password policy rejects weak passwords (a password containing the user’s own email address is refused).
  • Sessions use HttpOnly cookies: a 15-minute access token and a rotating 30-day refresh token; reuse of an old refresh token revokes the whole token family.
  • Cookie-authenticated mutating requests are protected by Origin/Referer checks, and cross-origin access is restricted to the configured front-end origin.
  • Provider credentials are Fernet-encrypted before storage; only the last four characters are ever shown, and the key is never returned by any API.
  • Rate limiting protects authentication, analysis, upload and credential-testing endpoints, with CAPTCHA verification available on abuse-prone operations; logs and error reports are scrubbed of passwords, tokens, keys and SRS text.
ThreatMitigation in the System
SQL injectionAll database access through SQLAlchemy parameterised queries; no string-built SQL
Cross-site scripting (XSS)React’s automatic output escaping; security headers; no raw rendering of user content
Cross-site request forgery (CSRF)Origin/Referer verification on cookie-authenticated mutating requests
Session hijackingHttpOnly cookies, short access-token life, refresh rotation with reuse detection and family revocation
Credential stuffing / brute forcePer-endpoint rate limits, CAPTCHA support, Argon2id hashing cost
Insecure direct object referenceOwner-wise filtering in repositories and endpoints; foreign identifiers return 404
Malicious file uploadMagic-byte and size validation, extraction budgets, server-generated storage names, no execution of uploaded content
Secret leakageEncrypted credential vault, hashed tokens, scrubbed logs and error reports, secrets only in environment variables

10.2 Privacy

Analyses, documents and credentials are private to their owner by construction. The user can export the data held about them, purge analysis history, set a history-retention preference, and delete the account completely, which removes all owned rows and stored files. Requirement text is never written to application logs or error reports. Where the optional enhancement is used, the report discloses that an external provider processed the content, and this happens only with credentials the user personally supplied.

10.3 Testing Approach and Results

Testing was carried out at four levels: unit tests for each detector, the scoring formula, deduplication and segmentation against fixed examples including a curated corpus of requirements with expected findings; integration tests of the API and services against a real PostgreSQL database, covering authentication, analysis persistence, document processing, ownership isolation, the credential vault and privacy operations; interface tests of front-end components and pages with Vitest and Testing Library; and system testing by executing the complete application and running the demonstration of Section 9.4 through the browser.

Overall, the project meets the objectives of Chapter 3. Its strongest qualities are the explainability of every finding, the reproducibility of the deterministic engine, and the completeness of the surrounding product — accounts, documents, reports, history, dashboard, privacy — which makes it usable as a real working tool rather than a demonstration of a single algorithm.

11.2 Limitations

  • Detection is heuristic: acceptable phrasing can occasionally be flagged, and ambiguity needing domain knowledge cannot be detected; findings are review aids, and the score is a comparative indicator, not a certification.
  • Scanned or image-only PDFs cannot be analysed (no OCR); analysis is English-first.
  • Rate limiting operates within a single server process; a shared limiter would be needed for very large multi-instance deployments.

11.3 Future Enhancements

  • Team workspaces: shared analyses, comments and review assignments.
  • Report export: download of the analysis report as a formatted PDF or DOCX document.
  • Batch and CI integration: an API or command-line mode to check SRS quality in a build pipeline.
  • OCR and multilingual support: text recognition for scanned documents; detector packs for more languages.
  • Configurable detector packs: organisation-specific terminology, glossaries and severity policies; deeper checks such as duplicate-requirement detection.
  • Distributed rate limiting and a native mobile application reusing the same back-end API.

12. Conclusion

Requirement statements written in natural language are frequently vague, subjective, incomplete or unverifiable, and the resulting misunderstandings cause rework and defects that are discovered late and cost much to repair. The literature study confirmed that a large part of this weakness follows recognisable wording patterns and can therefore be detected automatically, provided the findings remain explainable to the human analyst. The SRS Ambiguity Detector developed in this project meets that requirement. It is a complete web application — not merely a demonstration of an algorithm — in which a verified user can paste SRS text or upload a PDF, DOCX or TXT document and within seconds receive a requirement-by-requirement report: eleven categories of findings, each with the exact phrase, severity, reason and recommendation; a transparent score out of 100 with an ambiguity band; and four health dimensions showing where a document is weak. Analyses are preserved in PostgreSQL, so reports can be reopened, history searched, and quality trends observed on a dashboard. An optional enhancement can add an overview and rewrite suggestions via the user’s own encrypted credentials, while the deterministic engine remains the authoritative source of every result. Security and privacy (Argon2id hashing, rotating cookie sessions, owner-wise isolation, encrypted vault, rate limiting, export and deletion) were treated as core requirements.

Verification: 591 back-end and 432 front-end tests (1,023 total) pass, the production build succeeds, and a live demonstration produced consistent findings (73/100, Moderate, 18 issues across 7 requirements) via both input paths. It serves students, analysts, developers, testers and small teams at very low operating cost. The project thus demonstrates the complete journey from an identified problem, through literature study, feasibility analysis, design, implementation, security, testing and deployment planning, to a working product with a credible path to real use, and it provides a firm base for the future enhancements recorded in Chapter 11.
